# 청년정책 매칭 에이전트 (1단계: 추천만)

내 프로필(엑셀로 입력)과 공식 소스 데이터를 비교해서 지원 가능한 청년정책만 걸러
엑셀로 저장하는 스크립트. 결과 엑셀에는 마감일과 신청링크가 반드시 채워진 항목만
"매칭결과" 시트에 올라감. 신청서 자동 작성/제출은 범위 밖 — 그건 별도 2단계.

## 데이터 소스

- **온통청년(youthcenter.go.kr)** — 공식 Open API. 회원가입 + 인증키 발급만 받으면
  된다.
- **청년몽땅정보통(youth.seoul.go.kr) "청년지원정보" 게시판** — 서울시가 자체 운영하는
  사이트라 공식 Open API가 없다. 사용자가 이 소스는 반드시 가져와야 한다고 명시적으로
  요청해서, HTML 파싱(크롤링)으로 통합했다(`src/seoul_youth_client.py`). profile의
  거주_시군구가 서울 자치구일 때만 자동으로 동작하고, 그 외 지역이면 건너뛴다.
  `config.yaml`의 `sources.seoul_youth.enabled: false`로 끌 수 있다.
  목록 페이지엔 나이/학력 같은 구조화된 자격조건이 없어서, 마감 안 된 항목은
  상세페이지까지 한 번 더 가져와 자유 텍스트 자격조건은 LLM 소프트필터로 넘기고,
  "담당기관 바로가기" 외부 링크가 있으면 신청링크도 그걸로 교체한다
  (`sources.seoul_youth.fetch_details: false`로 끄면 목록 정보만 씀, 더 빠름).

두 소스 모두 없어도(예: 네트워크 오류) 파이프라인 전체가 죽지 않는다 — 소스 하나가
실패하면 그 소스만 오류로 기록하고 나머지 소스로 계속 진행한다. 실행할 때마다
콘솔과 결과 엑셀의 "안내" 시트에 소스별 수집 건수/오류가 남는다.

## 시작하기

### 1. API 키 발급 (직접 해야 함, 대신 못 해줌)
1. https://www.youthcenter.go.kr 회원가입 (본인인증 필요)
2. 로그인 후 마이페이지 > 오픈(OPEN) API 메뉴에서 인증키 신청
3. 담당자 승인 후 키 발급 (승인까지 시간이 걸릴 수 있음)

### 2. 설치
```bash
cd youth-policy-agent
pip install -r requirements.txt
cp config.example.yaml config.yaml
```
`config.yaml`의 `api.api_key`에 발급받은 키를 넣는다.

### 3. 내 정보 입력 (엑셀)
`profile_template.xlsx`를 열어서:
- 2행(회색 글씨) = 작성 예시, 참고만 하고 지우지 말 것
- 3행(노란색) = 여기에 실제 내 정보 입력

**학적상태 / 취업상태 / 전공분야 / 가구유형은 드롭다운에 있는 표기 그대로 골라야 한다**
— 이 네 가지는 온통청년 공식 코드정의서(`docs/API코드정보.xlsx`)의 라벨과 정확히
맞춰서 자동 하드필터에도 쓰인다. 취업상태_상세/전공상세는 참고용 자유 텍스트라
필터링에는 안 쓰이고 LLM 소프트필터에만 넘어간다.

다 채웠으면 같은 폴더에 `profile.xlsx`로 저장한다(`config.yaml`의 `profile.file`이
이 이름을 가리킴). 거주지는 시/도 이름을 그대로 쓰면 됨(드롭다운 제공) — 내부적으로
법정동코드로 자동 변환됨. 서울 거주자는 시/군/구까지 적으면 5자리 코드까지 정밀
매칭되고(`지역코드표` 시트에 서울 25개 자치구 코드 있음), 그 외 지역은 아직 시/도
단위까지만 매칭된다.

### 4. 키 없이 먼저 동작 확인
```bash
python -m src.main --mock
```
`data/sample_policies.json`의 샘플 4건으로 필터링이 되는지 확인. `profile.xlsx`가
없어도 `--mock`은 목 프로필로 자동 대체돼서 에러 없이 동작한다(--mock 전용, 실제
신청 자격 판단에는 쓰지 말 것). `--mock`은 청년몽땅정보통 등 다른 소스는 건드리지
않고 온통청년 목데이터만 쓴다 — 완전히 네트워크/상태파일 없이 동작 확인용.

### 5. 응답 구조 확인이 필요하면
```bash
python -m src.main --inspect
```
2026-08-04 기준 실측 완료됨 — `src/matcher.py`의 `FIELD_MAP`/`CODE_MAPS`는 실제
API 응답으로 검증된 상태다. 원시 응답은 `output/inspect_response.json`에 저장된다
(콘솔에 바로 찍으면 Windows cp949 콘솔에서 일부 특수문자 때문에 깨질 수 있어서
파일로 저장하게 해뒀다). 온통청년이 나중에 또 API를 바꾸면 이 명령으로 다시 확인.

**참고(2026-08-04, `src/api_client.py` 주석에도 있음):** 온통청년 공식 문서
페이지의 "요청 예시" 섹션(`/opi/youthPlcyList.do?openApiVlak=...`)은 죽은 구버전
엔드포인트였다 — 실제로는 302로 내부망 포트(`:8080`)로 리다이렉트되며 응답이
전혀 안 왔다. 문서 페이지 안의 "테스트베스트" 버튼이 호출하는 JS 코드
(`apiReqExam` 함수)를 뜯어봐서 진짜 살아있는 엔드포인트
(`/go/ythip/getPlcy?apiKeyNm=...&pageNum=...&pageSize=...&rtnType=json`)를 찾아서
교체했다. 문서 페이지가 API 이전 후 예시 섹션만 업데이트가 안 된 것으로 보인다 —
만약 이 명령이 다시 안 되면 같은 방식(문서 페이지의 테스트베스트 JS 코드 확인)으로
새 엔드포인트를 찾아볼 것.

### 6. 실제 실행
```bash
python -m src.main
```
`output/matched_policies.xlsx` 생성됨. 시트 구성:
- **매칭결과**: 마감일 오름차순 정렬. 마감일·신청링크가 둘 다 확인되고 상태가
  "신청가능"인 것만.
- **확인필요**: 나머지 전부 — 상태 컬럼으로 이유를 구분한다.
  - `신청예정`: 아직 접수 시작 전이라 마감일/링크가 없는 것뿐, 파싱 실패가 아님.
    신청기간이 짧은 정책이 이번 수집 시점엔 안 열려 있다가 다음 수집 전에 열렸다
    닫혀버리는 걸 막기 위한 것 — 미리 "언제 열리는지" 알 수 있게 남겨둔다.
  - `마감`: 이미 지난 공고.
  - 그 외: API/사이트 응답에서 마감일 또는 링크를 못 뽑은 것 — 원문 확인 필요.
- **신규** 컬럼: 지난 수집 회차 이후 처음 나타난 항목이면 "신규"로 표시(증분수집
  상태 참고).

## 프로젝트 구조
```
youth-policy-agent/
  config.example.yaml      # 설정 템플릿 (API키, profile.file 경로, 소스 on/off, 출력 경로)
  profile_template.xlsx    # 내 정보 입력 템플릿 (채워서 profile.xlsx로 저장)
  docs/API코드정보.xlsx      # 온통청년 공식 코드정의서 (CODE_MAPS의 근거)
  src/
    api_client.py           # 온통청년 API 호출
    seoul_youth_client.py    # 청년몽땅정보통 HTML 파싱 (공식 API 없는 소스)
    matcher.py                # 하드 필터(나이/지역/소득/혼인/학력/취업/전공/특화대상) + 스코어링
                               # FIELD_MAP, CODE_MAPS 여기 있음
    llm_check.py               # 소프트 필터: 자유 텍스트 자격조건 LLM 판정
    profile_io.py                # profile.xlsx → Profile 객체 파싱 (지역명 → 법정동코드 변환)
    output_xlsx.py                 # 매칭 결과 → 엑셀 저장 (마감일/링크 필수 + 상태 판정)
    collector_state.py              # 증분수집 상태(data/collector_state.json) 읽기/쓰기,
                                     # 반복 노출 억제(should_show) 판단
    dedup.py                         # 온통청년×청년몽땅정보통 간 같은 정책 교차 중복 제거
    main.py                          # 실행 진입점 (--mock, --inspect, --no-llm, 기본 실행)
  data/
    sample_policies.json    # 목데이터 (키 없이 테스트용)
    collector_state.json    # 증분수집 상태 (자동 생성, gitignore 대상)
  tests/                     # 단위 테스트 (matcher, output_xlsx, profile_io, collector_state, dedup 등)
  output/                    # 결과 저장 위치 (gitignore)
```

## 필터링은 2단계

1. **하드 필터** (`matcher.py`): API/사이트가 코드·숫자로 주는 조건을 규칙으로
   정확히 판단.
   - 나이, 지역, 혼인상태(mrgSttsCd), 소득상한(earnCndSeCd가 "연소득"일 때만)
   - 학력(schoolCd), 취업상태(jobCd), 특화대상/가구유형(sbizCd), 전공계열(plcyMajorCd)
     — 정책 쪽 값이 "제한없음"이면 무조건 통과, 프로필 쪽이 비어있어도 배제하지
     않음(오배제보다 확인필요로 넘기는 게 낫다는 원칙).
2. **소프트 필터** (`llm_check.py`): `addAplyQlfcCndCn`(추가 자격조건),
   `ptcpPrpTrgtCn`(참여제한대상) 같은 진짜 자유 텍스트 조건만 규칙 파싱이 안 되니까
   Claude에게 판단시킴. 결과는 eligible / excluded / not_sure 셋 중 하나.

소프트 필터를 쓰려면 환경변수 `ANTHROPIC_API_KEY`가 있어야 함:
```bash
export ANTHROPIC_API_KEY=sk-ant-...
python -m src.main
```
키가 없으면 에러 없이 건너뛰고 전부 "검토 필요"로 표시됨. `--no-llm`으로 명시적으로
생략할 수도 있음.

## 증분 수집 (data/collector_state.json)

정책을 한 번 긁어온 뒤 다음 수집 때 처음부터 전체를 다시 LLM으로 재판정하지 않도록,
소스별로 "이전에 본 정책 + 그때 판정한 verdict + 그때 상태"를 로컬에 저장해둔다
(`collector_state.py`). 같은 정책이고 자격조건 텍스트도 안 바뀌었으면 캐시된
verdict를 재사용해서 LLM 호출 비용을 아낀다. 텍스트가 바뀌었거나 새 정책이면 다시
판정한다. `--mock` 실행은 이 상태 파일을 안 쓴다(순수 동작 확인용이라 실제 수집
이력과 섞이면 안 되므로).

**반복 노출 억제는 기본 꺼짐 (2026-08-05 변경, issue #3)**: 상태가 지난 회차와
같으면 이미 본 정책을 결과에서 빼는 기능을 만들어봤는데, "매칭결과" 시트는 새
소식 피드가 아니라 "지금 신청 가능한 것" 목록이라서 — 상태가 안 바뀌었다고
화면에서 빼버리면 아직 신청 안 한 정책을 사용자가 놓칠 수 있었다. 그래서 기본은
**매 회차 지금 유효한 것 전부를 항상 보여주는 쪽**(결과적으로 계속 누적되는
것처럼 보임)으로 바꿨다. 필요하면 `config.yaml`의 `output.hide_repeats: true`로
다시 켤 수 있다(코드는 남겨둠).

이거랑 별개로 **"중복 작업 방지"는 계속 동작한다** — LLM verdict 캐싱(조건
텍스트가 지난 회차와 동일하면 재호출 안 함)은 화면 노출과 무관하게 항상 적용됨.
"화면에 뭘 보여줄지"와 "뭘 다시 계산하지 않을지"는 서로 다른 문제였다.

**소스 간 중복 제거**: 온통청년과 청년몽땅정보통은 완전히 독립적으로 수집돼서 같은
실제 정책이 양쪽에 다 올라올 수 있다. 온통청년이 정상 수집됐을 때만, 제목 유사도
(`dedup.py`, 기관명/날짜 표기 차이는 정규화 후 비교)로 겹치는 걸 찾아서 청년몽땅정보통
쪽을 제거하고 온통청년 쪽(구조화된 하드필터 정보가 있어 더 정확)을 남긴다. 오탐(서로
다른 정책을 중복으로 착각)보다 미탐이 안전하므로 임계값은 보수적으로 잡혀있다 —
2026-08-04에 실제 데이터로 검증됨: 서울 자치구 기준 한 회차에서 "정신건강 심리상담
바우처사업"(청년몽땅정보통 표기)과 "정신건강 심리상담 바우처 사업"(온통청년 표기)을
정확히 같은 정책으로 잡아냄, 오탐은 없었음.

## 마감일/링크가 "필수"인 이유
결과 엑셀을 보고 바로 신청 액션을 취할 수 있어야 하므로, `output_xlsx.py`는 마감일
파싱에 실패했거나 신청링크가 없거나 이미 마감/아직 미개시인 항목을 "매칭결과" 시트에
절대 넣지 않고 "확인필요" 시트로 분리한다. 자동 신청 자체는 아직 없지만(2단계),
최소한 사람이 "뭘, 언제까지, 어디서 신청해야 하는지"는 한 번에 보여야 한다는 원칙 —
느슨하게 풀지 않는다.

## 지금 로직의 한계
- 소프트 필터는 정책 설명 텍스트만 보고 판단하므로, 텍스트 자체가 모호하면 LLM도
  not_sure로 넘김 — 이 경우는 사람이 신청 페이지를 직접 봐야 함.
- 스코어링은 "관심분야 일치하면 우선순위 올림" 정도의 단순 규칙.
- `FIELD_MAP`/`aplyYmd` 형식/코드값은 2026-08-04에 실제 API로 검증 완료(위 "5. 응답
  구조 확인" 참고). `jobCd`/`plcyMajorCd`는 콤마로 구분된 다중값이 실제로 확인돼서
  `matcher.py`가 OR 비교로 처리하게 반영해뒀다(하나라도 프로필과 맞으면 통과).
- 지역 매칭은 서울만 자치구 단위, 그 외 시/도는 아직 시/도 단위까지만.
- 청년몽땅정보통 소스는 목록 페이지의 상태 배지/제목 속 "(~월/일)" 표기에 의존하는
  크롤러라 사이트 개편에 취약함 — 구조가 바뀌면 조용히 0건으로 보이는 대신 예외를
